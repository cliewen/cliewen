# PDR-029 — Simplification is judged by two tests, chosen by surface

## Context and problem statement

[PDR-013](PDR-013-explicit-core-red-line.md) supplies simplification's criterion — *does the core need it?* — and records why simplification kept stalling without one: every debate was argued case by case, and protection with no boundary became uniform friction. That criterion is correct for what it was written about. It decides whether a rule, an artifact type, a required field, a command, or a check earns its place, and it decides it without appeal to taste.

It returns the wrong answer on one surface, and that surface is the one an adopter reads most closely. Applied to Cliewen's own methodology carriers — the skills, the routing hub, the guide — nearly every rule stated there *is* needed by the core, so the test passes almost everything and concludes there is nothing to simplify. What makes those carriers expensive is not unnecessary rules. It is the same necessary rule stated in several places; a rule compressed so far that a reader cannot tell whether it has been satisfied; statements tied to nothing a reader can open; and an order that puts the least violable rules last.

The tie to the corpus is what the criterion is least able to see, and it matters most, because the skills are read adversarially. A reviewer examining a skill closely does not ask whether the file is short. They ask, of a particular sentence, *why do you have this statement?* — and a methodology whose own instructions cannot point at the decision behind a rule has lost the argument before any of its rules are evaluated. Cliewen already demands exactly this of a product: every behavior traceable to a criterion, every criterion to a capability, every capability to a goal. Its own instructions are the one surface where that discipline was never applied, and a methodology that does not hold itself to its central claim is arguing against itself.

Order is the other half, and it is invisible to every per-statement test. In this repository's own skills the review boundary — which states that an agent never merges its own pull request and never pushes to `main` — is the final section of both `clue-delta` and `clue-verify`, past three-quarters of each file, after the procedure it constrains. The tier rules that decide whether the skill applies at all sit below the loop that assumes it does. Nothing there is untrue, duplicated, or uncheckable; the file is simply arranged so that a reader who stops early has read the procedure and not the prohibition.

None of the four is a matter of taste, and each is settled by inspection rather than opinion. Duplication is countable: shared fragments are rendered into more than one skill, and because the change loop directs an agent from one skill to another that renders the same fragments — while the routing hub has already stated several of them — an ordinary full change re-reads a substantial fraction of the instruction it has already read. Compression's cost shows in the same files: a verification item stating five independent conditions in one sentence is offered as a single checkbox, which no reader can honestly tick when four conditions hold and the fifth does not. Tracing is settled per statement by naming the artifact behind it and seeing which statements have none. Order is read straight off the file. The arithmetic and the register both belong to the inventory P-013's M-062 performs, not to this record; what is enduring here is that all four failure modes exist and that none is visible to *does the core need it?*

A campaign judged only by PDR-013 would not see any of that, and would defer simplification a fourth time on the grounds that everything passed.

## Decision outcome

**Simplification is judged by two tests, and the surface decides which one applies.**

- ***Does the core need it?*** governs rules, artifact types, required fields, commands, checks, and anything else whose existence changes what the method obliges. [PDR-013](PDR-013-explicit-core-red-line.md) is unchanged and remains the test of record for this surface.
- ***Does every statement trace, state its rule once, and admit checking?*** governs carrier prose: skills, the routing hub, contributor and public guidance, and CLI text. The unit is the individual statement, not the file, and it must pass all three conditions. It **traces** when a live corpus artifact — a decision, constraint, goal, or acceptance criterion — **states the rule the statement carries**, and the register names that artifact. It **states its rule once** when no live carrier already states the same rule in the same reading path. It **admits checking** when a reader can determine whether it has been satisfied.

  Tracing is the operative condition, and it is mechanical only because it is bounded to what the traced artifact actually says. **Derivability is not a trace.** Nearly every statement in every carrier can be argued from [G-001](../goals/G-001-verifiable-thread.md) or a broad constraint, so a trace to an artifact the rule could merely be *reasoned toward* is no evidence at all — it would let the whole skill set pass at once and return "nothing to do", which is the fourth deferral reached through a new test rather than the old one. The register therefore names the **narrowest** artifact that states the rule, and a statement whose only candidate is a goal or a general constraint is recorded as tracing to nothing.

  This is the discipline Cliewen already demands of a product, applied to itself at the same strength: a behavior traces to the criterion that *states* it, never to the goal it can be argued from. The question a human reviewer asks when reading a skill closely is *why do you have this statement?*, and the only answer that survives is an artifact the reader can open and find the rule in. "It seemed wise", "it has always been there", and a rationale that exists solely in the statement itself are not answers. A statement can be unique in the corpus and perfectly checkable and still fail, by being a true sentence tied to nothing.

**A trace is not automatically a justification, and an untraceable statement is not automatically waste.** Both failures point at the corpus rather than the sentence. A statement that traces cleanly to a decision may still be one Cliewen should stop making, because the decision behind it has outlived its reason — the reach of the test therefore extends upstream to the decision itself, asking not only whether it was made but whether it still makes sense and is still important enough to bind every future change. A statement that traces to nothing may equally be a real rule nobody ever recorded, in which case the repair is to write the missing decision, not to delete the sentence. **Neither case is settled by an agent.** Each becomes an open question naming the statement, what it traces to or fails to, and what removing it would cost, and the human answers it; a recorded answer becomes a decision under [C-011](../constraints/C-011-decision-records-typed.md). Silent deletion and silent retention are the same failure, and both are forbidden here.

**The trace is recorded about the carrier, never inside it.** A skill states rules; it does not cite the corpus, and no marker, identifier, or footnote is added to carrier prose to make tracing work. The reader of a skill should meet the rule, not its provenance. Where the trace is kept, and how a record stays bound to prose it does not annotate, is a mechanism question P-013 answers with evidence rather than one this decision settles in advance; what is decided here is that the burden falls on the register and not on the carrier.

**Carrier statements are ordered by how binding they are, most binding first.** Order is a property of the carrier rather than of any statement, and it is load-bearing for the same reason the rules exist: a reader who stops early, or an agent that acts before finishing the file, must already have read what it may not violate. A carrier that states its inviolable boundaries after the procedure they constrain has ordered itself so that the cheapest reading is the least safe one, and that is a defect of the carrier even when every statement in it passes all three conditions.

**Fewer rules that hold beat more rules that overlap.** Where two statements cover the same ground, the campaign's preferred outcome is a single rule that covers both, not two rules plus a note about which wins. Overlap is not merely wasted words: two rules addressing one situation is how ambiguity enters a methodology, and an ambiguous rule is worse than an absent one because it is obeyed inconsistently while appearing to be obeyed. Consistency of the surviving set therefore outranks the completeness of any individual rule.

  This is a different defect from the duplication condition above, and the two have different repairs. **One rule stated twice** — the same obligation restated in another carrier on the same reading path — is deduplicated: one statement survives unchanged and the restatement goes. **Two rules over one situation** — distinct obligations, overlapping scope, no stated precedence — is merged into a single rule covering the union. The discriminator is whether a reader following both statements could ever be pulled in different directions: if not, it is a restatement; if so, it is an overlap, and it is the case that produces ambiguity rather than mere length.

**Word count is not the measure of success, and the second test will sometimes lengthen a passage.** Splitting an unreadable five-condition sentence into five checkable ones adds words and is a pass, not a regression. The campaign's measure is the set of rules that survive: each traceable, each stated once in a given reading path, each checkable, ordered by how binding it is, and consistent with every other rule in the set — never the size of the diff. A campaign that scored itself on words removed would repair the duplication and make the compression worse.

**Carrier prose and corpus artifacts are not equally safe to compact.** Carrier prose is instruction: it may be rewritten, merged, or moved freely so long as every rule it carries survives somewhere in the reading path. The corpus is the memory that multiple humans and coding agents share, and its obligation is that a different reader, later, recovers the same meaning. Reducing what the corpus can remember, or making a past decision harder to reconstruct, is not simplification, and passing *does the core need it?* does not by itself license it. Within this campaign, any such removal carries its own decision record and a guard proving what still resolves; this clause states how P-013 judges its own candidates and adds no obligation to changes outside it, which continue to retire artifacts under [ADR-034](ADR-034-retirement-is-deletion.md) and the `supersedes:` mechanism unchanged.

**This decision authorizes the tests, not any removal.** Every milestone that changes what a command asserts, or that touches the verifiable thread, the human merge boundary, or the judge, remains core-adjacent under [C-013](../constraints/C-013-core-changes-need-decision.md) and carries its own record in its own change.

## Rejected: apply *does the core need it?* to every surface

It is the single-criterion answer and it is the reason simplification has been deferred four times. On carrier prose the test passes nearly everything, because the rules genuinely are needed; the cost lives in how many times a rule is stated, how checkable each statement is, whether anything in the corpus stands behind it, and the order the statements are read in — none of which the criterion can see. One criterion that returns "nothing to do" on the largest reader-facing surface is not a boundary, it is an exemption.

## Rejected: measure the campaign in words or artifacts removed

A count is tempting because it is deterministic, and it is precisely wrong here. It scores the duplication repair and the compression repair with opposite signs, so an agent optimizing it would delete the second copy of a rule and then compress the survivor until nobody can check it — arriving at a corpus that is smaller and less usable, which is the outcome [G-001](../goals/G-001-verifiable-thread.md) exists to prevent. It is blind to the two repairs that cost nothing in words at all: writing the missing decision an orphaned statement should have traced to, and reordering a carrier so its inviolable rules precede the procedure they bind.

## Rejected: remove the duplication by making skills reference each other

[ADR-021](ADR-021-generated-standalone-skills.md) considered exactly this and rejected it, so that copying one skill folder yields complete instructions with no dependency on a repository layout outside itself. That reasoning is untouched here. The file-level repetition is deliberate and is not the cost this decision targets; the second test's duplication condition is about repetition inside a single reading path, which is a different quantity and does not require reopening ADR-021. Its other conditions — tracing, checkability, and order — are properties of the authored source fragments and apply whatever the generator renders them into, so nothing in this decision depends on how many files a fragment reaches.

## Carrier

Four carriers state this decision and move together: this record, P-013's milestones and prose, the refinement blockquote in [PDR-013](PDR-013-explicit-core-red-line.md) that qualifies where *does the core need it?* reaches, and the curated index rows for this record and for P-013. The PDR-013 note is a live carrier in [PDR-019](PDR-019-methodology-contract-carriers-move-together.md)'s sense, not history — it states the carrier test in summary form inside a `verified` record that outranks this one at read time, so a change to the test that leaves it behind publishes a superseded rule from the more authoritative file. The index rows qualify for the same reason and one of its own: [C-016](../constraints/C-016-index-rows-state-their-record.md) makes curated row text part of the contract, and regeneration deliberately preserves a row whose target still exists, so a stale row is never repaired by any tool and no check will report it. Any change to the conditions updates all four.

The carriers this decision is applied *to* — the skills, the routing hub, the guide, contributor guidance, and CLI text — are edited by P-013's own milestones, not by the change that records it.
