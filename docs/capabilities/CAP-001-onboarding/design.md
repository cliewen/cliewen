# Design — CAP-001 Onboarding

## The command

`clue init [path]` materializes the whole convention in one call: the `/docs` taxonomy (folder READMEs that explain each record type, plus the decision log), the AGENTS.md routing hub, the five skills, and a CI workflow template. The scaffolding is embedded in the binary ([ADR-018](../../decisions/ADR-018-init-templates-embedded.md)): no network, no credentials, no checkout of this repo — the installed binary is the whole install.

- **Skills land twice**: `.agents/skills/` is the canonical location; `.claude/skills/` is the Claude Code mirror (`SKILL.md` spelling). The layout matches the first adopter repo, where it was proven by hand before being automated.
- **The CI template delegates its wall**: it emits a thin caller whose full commit reference points to Cliewen's upstream reusable validation workflow, with `clue-version` pinned to the emitted skill pair. The caller exposes only the JSON runner labels, `clue-source`, and writable `clue-install-directory`; the upstream workflow owns checkout, scope detection, the unarmed warning, checksum verification, acceptance-brief gate, and `clue validate --forbid-changes`. A fresh `init` repo is never red before its first change, and a vendored source stays loudly unarmed until its matching binary and `SHA256SUMS` exist.
- **Idempotent**: a re-run regenerates README index blocks (between `<!-- clue:index:start/end -->` markers) from folder contents — existing entries whose targets survive keep their hand-written descriptions, missing entries are appended — and touches nothing else. A pre-existing taxonomy README without markers gains an appended index block (prose intact), so an existing repo still reaches green; a lone or reversed marker is ambiguous, and init errors naming the file rather than guess at the block's bounds. A pre-existing folder without the README `validate` requires is named in the report (`missing`) — init never invents it. Existing files are **never replaced**: they are reported as skipped, so an adopter with their own AGENTS.md keeps it (the repo-local layer, ADR-013).
- **A symlinked directory is never written through** (AC-038): sharing an assistant's skills across checkouts makes `.claude/skills` — or `.claude`, or even `.agents/skills` — a symlink into a tree that belongs to more than this repository. Before emitting a file, `init` walks the target's ancestor directories *below* the root and skips the subtree when any of them is a link, reporting it as `linked` rather than folding it into the never-overwrite `exists` line: an empty mirror is then an informed choice rather than a mystery. The root itself is never inspected — a checkout reached through a link is ordinary — and nothing else the run emits is affected. This is emission only: `clue validate` still resolves a skill manifest through a link by design ([ADR-028](../../decisions/ADR-028-deterministic-skill-manifest.md)).
- **The template-vs-validator contract is a test, not discipline**: AC-002's test runs `clue validate` over a fresh `init` output, so a validator rule the templates violate fails the build the moment it lands.

## The guide

The quickstart page lives in the repo README; the command is the guide's most important layer and must not require reading anything. Layers, kept strictly separate:

1. **Command (seconds):** `clue init` — the foundation in one call.
2. **Quickstart (5 minutes):** README — install, `clue init`, first change loop, watch `validate` go green. Owned by [C-015](../../constraints/C-015-onboarding-under-30-minutes.md): under 30 minutes, reading nothing beyond the quickstart.
3. **Skills** — learned during use; the quickstart links each skill at the moment the reader's first change loop needs it (delta when they branch, verify before their first PR), never all four upfront. The system-level "why these skills" story lives in [architecture/skills.md](../../architecture/skills.md).
4. **Public guide** — the why and the full working model for newcomers who are not yet inside a Cliewen repository. It is a handwritten VitePress site under `/guide`, kept outside the corpus and deployed by the architecture in [ADR-023](../../decisions/ADR-023-public-guide-architecture.md), with [ADR-024](../../decisions/ADR-024-custom-domain-root.md) making `https://cliewen.dev/` its canonical root. The root README remains the shortest mechanical path; the guide adds depth without adding a prerequisite before first green validate.

The generated corpus explains itself: each emitted folder README says in plain language what its record type is and when a change updates it, and the emitted `docs/README.md` carries the map ("what lives where — and when a change updates it"). The guide points into the generated repo instead of duplicating it.

## Guide requirements (accumulating)

Lessons about what the guide must contain, appended the moment they are learned:

- **Prerequisites must be explicit** (learned 2026-07-12): git, the `clue` binary, and — for the PR-based change loop as practiced — an authenticated `gh` CLI. The loop works with plain git and any forge; `gh` is the convenient path, not a dependency of the method.
- **Skills are guide layer 3, learned during use** — see layer list above.
- **Value precedes vocabulary** (learned 2026-07-22): the public front door names the agent-written-change problem, intended audience, concrete outcome, and the distinction between Cliewen, `clue`, and the corpus before asking a newcomer to learn the taxonomy.
- **The first proof is disposable and observable** (learned 2026-07-22): Getting Started reaches the C-015 green scaffold first in an empty Git repository, then activates a draft criterion without evidence so the released validator produces its real missing-test diagnostic; ownership, recovery, and full-directory cleanup are explicit.
- **The manual release-binary route stays documented as the fallback** (learned 2026-07-22 as "release binaries are the primary install path"; revised 2026-07-27 by [ADR-030](../../decisions/ADR-030-verified-install-scripts.md), which made the verified install script primary and this route the documented alternative beneath it): a compact platform table identifies the published architecture asset, and short manual steps verify it against `SHA256SUMS`, put it on the user `PATH`, and show the version result. The unsigned macOS path names the checksum-first Gatekeeper exception explicitly, which still applies to a browser download. Source installation stays secondary, so using Cliewen does not appear to require Go.
- **A verified install script may lead, because the alternative disappeared** (learned 2026-07-27): the original rule kept installer scripts out of the first encounter while a package manager was assumed reachable. Homebrew formulas were then deprecated and casks are macOS-only, leaving no single package manager that covers all three platforms, so the choice became a script or six manual steps rather than a script or `brew install`. A script may lead only on the terms [ADR-030](../../decisions/ADR-030-verified-install-scripts.md) sets: served from the project's own domain, readable before it is run, verifying the download against the release's published `SHA256SUMS` before writing anything, and needing no elevation. The manual steps stay documented directly beneath it, so nobody is forced through a pipe into a shell.
- **A plugin may carry the install, never the skills** (learned 2026-07-27, [ADR-031](../../decisions/ADR-031-plugin-ships-a-bootstrap-only.md)): a coding agent has its own distribution channel, and reaching it removes the context switch the install script still costs a reader already in a session. What the channel must not carry is the five lifecycle skills. They are committed repository files stamped with the writing binary's version, and a plugin's components are per-user cache copies that `checkSkillVersions` cannot see — one copy across every repository the user opens, where the point of a stamp is that it is pinned per repository. The plugin therefore ships one bootstrap that installs the binary, pins no version, and asks before `clue init`. The guide page carrying this channel exists mainly to state what it does not install, because a bundled skill set is the shape every reader will expect.
- **The guide distinguishes machine and method guarantees** (learned 2026-07-22, corrected after the v0.9 carrier audit): `clue validate` classifies and counts supported Go, per-executable JVM, and Cucumber evidence for criteria declaring a machine proof type, recognizes `(single-direction)`, treats a Human declaration as requiring no code evidence, recognizes per-criterion `@draft`, and preserves one supported reference for unannotated legacy criteria. JVM identity, type, and direction belong to one supported Java or Kotlin executable rather than a file-level tag cross-product. The judge neither runs tests nor inspects whether the acceptance brief supplies Human proof; normal test runners, the pull request workflow, and human review remain responsible for execution and meaning.
- **CI enforcement must be reproducible** (learned 2026-07-22, revised by [ADR-038](../../decisions/ADR-038-upstream-validation-workflow.md)): the guide gives the thin caller's immutable workflow reference, the exact vendored or release-source checksum path, the demonstrated self-hosted/no-root inputs, the unarmed warning and armed `--forbid-changes` run, the minimum protected-branch contract, and a disposable failing-pull-request probe.
- **Adoption starts with the smallest useful thread** (learned 2026-07-22): begin with a goal, capability, acceptance criterion, and its honest acceptance evidence — classified positive/negative executable references or the Human acceptance brief. Add plans, decisions, constraints, architecture, and analysis only when their triggering problem exists, and state the repository and workflow conditions that make Cliewen a poor fit.
- **Operations must name the support boundary and recovery path** (learned 2026-07-23): the public guide distinguishes released binaries, the Go, Java/Kotlin, and Cucumber evidence harvesters, generated skill locations, the GitHub workflow, and repository-local validation from broader methodology intent. It gives a coordinated binary/skills/CI upgrade path, keeps `init`'s skip behavior explicit, and treats extraction, adoption, and uninstallation rollback as reviewed repository work rather than a bypass. Every guide page ends in one primary next action, checked by AC-036's classified positive and negative tests.
