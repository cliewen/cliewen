# Design — CAP-004 `clue ships`

## Version surface

`cmd/clue` carries `var version = "dev"`. Release builds override it with `-ldflags "-X main.version=<semver>"`; when no stamp was injected, `main` falls back to the module version Go embeds in `go install module@vX.Y.Z` builds (`debug.ReadBuildInfo`, `v` trimmed to bare semver) — `(devel)`, a pseudo-version (branch/commit install, or the VCS-derived version a checkout build embeds since Go 1.24), and a `+dirty` suffix (local modifications) all stay `dev`. `clue version` and `clue --version` print `clue <version>` (via `runVersion(io.Writer)`, so the AC test can capture it). `runValidate` threads the same package var into `corpus.Options.Version` so the drift rule can compare.

## Skill stamps and the drift rule

Each Cliewen skill lives at `.agents/skills/<name>/skill.md` and declares `cliewen-skill: true` plus `version:` in its frontmatter. `corpus.checkSkillVersions` (wired into `Validate`) reads skill frontmatter directly from disk — skills sit outside the `docs/`+`changes/` scan, like `checkFolderReadmes` already reaches past the artifact graph. Ownership is resolved before version checks ([ADR-022](../../decisions/ADR-022-skill-ownership-marker.md)):

1. **Ownership scope (AC-029)** — only a skill whose marker is boolean `true` joins the Cliewen set. An absent marker leaves an unrelated skill unmanaged; a present value other than boolean `true` is malformed and fails.
2. **Reserved managed slots (AC-082)** — the six canonical Cliewen directory names are reserved managed slots. An unmarked skill in one of them fails with reinstall guidance, so a released binary cannot silently ignore a managed skill. Unmarked skills under every other name remain outside the set.
3. **Stamp present (AC-031)** — a marked skill with no frontmatter `version` fails. Runs on every build; malformed frontmatter and non-string versions (YAML reads `1.0` as a number) are named as such, not as missing stamps.
4. **Set consistency (AC-032)** — marked skills must agree on one version. The reference is the version the majority of marked skills carry (ties go to the earliest-sorted holder), so the report names the actual outlier. Per-skill markers, kept a set by the rule ([ADR-011](../../decisions/ADR-011-version-stamping.md)). Unmarked skills do not vote.
5. **Drift vs the binary (AC-033)** — only when the marked skills already agree *and* the binary is a real release (`version` is neither `""` nor `dev`): each marked skill version must equal the binary's, else it is drift. `dev`/source builds skip this — the preview contract is "OK (skips drift)". This is what an adopted repo's installed (released) `clue` uses to answer "are my Cliewen skills current?".

Issues sort into the same `path: message` stream as every other rule.

## Skill authoring and generation

The complete skill directories are the installed artifacts, with their `skill.md` entry points carrying the ownership and version markers described above. Authoring remains centralized under `internal/skills/source/` ([ADR-021](../../decisions/ADR-021-generated-standalone-skills.md)). Skill-specific templates compose shared instruction fragments at generation time; the generator emits each section as a local reference and emits its read condition in the short entry point. No generated skill directory has a runtime dependency on another skill or on the source tree ([ADR-059](../../decisions/ADR-059-progressive-standalone-skill-directories.md)).

`go generate ./internal/skills` writes both `.agents/skills/` and `internal/scaffold/templates/skills/`. The generator owns the six `clue-*` directories in both trees, including routed references and `clue-extract` resources, and normalizes output to LF for deterministic bytes. AC-137 tests exercise generation into an empty repository, prove that every routed local reference exists and both trees agree, and reject missing, changed, or unexpected entry points or references. A Sanity test checks the committed outputs against the same in-memory rendering, so editing any generated file instead of its source fails the build.

## Release pipeline

Cutting a release is merging the pull request that raises the version ([PDR-015](../../decisions/PDR-015-merging-cuts-the-release.md)). `.github/workflows/tag-on-merge.yml` runs on every push to `main`, reads the version from the skills' frontmatter template — the single bump site, and the same input the drift gate below judges the tag against — and releases only when that stamp changed in the pushed merge and its version is not already tagged. A workflow-level concurrency lock makes that decision, tag push, and release dispatch one critical section, so a later ordinary merge cannot observe the untagged version and tag its own checkout. Every other merge exits quietly. A releasing merge must clear the gates in `.github/scripts/release-gates.sh` before anything else happens: a non-empty `## [X.Y.Z]` section, and — when the change touches `internal/migrate` — a non-empty `### Migration` subsection within it ([ADR-039](../../decisions/ADR-039-versioned-corpus-migrations.md)). Those gates live in a script rather than in the workflow because CI runs the same script on every pull request, where a release that could never be tagged fails while it is still a proposal. Running them only at merge time was too late to be actionable: tagging fires only on the merge that raises the stamp, so a release rejected there cannot be retried and the number has to be abandoned — which is how 0.11.1 was lost. The script reads the stamp and the changelog out of the ref it is given rather than the working tree, and is a no-op for any change that does not raise the stamp. `tag-on-merge` remains the authority; when the pull-request base is unresolvable the CI run is skipped and the merge-time run still guards the tag. Past the gates it tags the merge commit and dispatches the release. The dispatch is necessary rather than stylistic: a tag pushed with `GITHUB_TOKEN` does not trigger workflows, and `workflow_dispatch` is the documented exception, so the release starts without introducing a personal access token.

`.github/workflows/release.yml` triggers on `v*` tags (and `workflow_dispatch`, which a guard restricts to tag refs — dispatching from a branch fails before any build, so nothing can stamp binaries as a branch name or publish a branch-named release; that same guard is what makes the dispatch above safe). The release body is the tag's `## [X.Y.Z]` section of `CHANGELOG.md`, extracted verbatim; a missing or empty section fails the release before anything is built, and `TestSanity_ReleaseNotesComeFromChangelog` keeps auto-generated notes from returning ([ADR-012](../../decisions/ADR-012-release-notes-from-changelog.md)). The tagged tree also contains `.github/workflows/clue-validation.yml`, the upstream validation unit that thin callers reference. Release tags used by module-built callers must be protected from force updates. The version gate described below runs next, then `go test ./...` — a tag can land on any commit, so nothing ships untested.

Building and publishing is then one goreleaser step ([ADR-030](../../decisions/ADR-030-verified-install-scripts.md)), pinned by commit SHA because it runs with `contents: write`, and pinned to an exact goreleaser version because that step renders the asset names ADR-030 makes a public contract — a floating range could change either without a change here. goreleaser refuses to build from a dirty tree, so the extracted `release-notes.md` is git-ignored; leaving it untracked fails the release at the publish step, after the gate and the tests have already passed. `.goreleaser.yaml` — not the workflow — defines the build matrix, the stamp, the asset names, and the checksum file, so the release's published interface has one definition. It cross-compiles linux/darwin/windows × amd64/arm64 with `CGO_ENABLED=0` and `-trimpath`, stamps `main.version` from the tag, and reproduces byte-identical builds by embedding the commit timestamp rather than the runner's clock. The extracted notes reach the release body through `--release-notes`, which is by itself what keeps goreleaser's commit-log generator out; the config deliberately carries no `changelog:` block, because `disable: true` there is documented to discard the supplied notes as well and did exactly that to v0.8.0. What holds ADR-012 now is the step after publishing: the workflow reads the release body back from GitHub and fails if it is not the extracted section, normalising line endings and trailing blank lines so the check fails only on real divergence. Git tags carry the conventional `v` prefix (Go module tagging); goreleaser's `{{ .Version }}` is the tag with that `v` already stripped, which is the bare semver the skills' frontmatter carries — the drift rule then compares like against like.

Every release publishes **both** asset shapes under one `SHA256SUMS`: the bare binaries under the exact names the hand-rolled loop used (`clue-<version>-<os>-<arch>`, `.exe` on Windows), and `tar.gz`/`zip` archives a later package-manager channel can consume. That checksum file lists upload names, so both sources verify by name: `clue-source: vendored` selects the vendored binary's entry from the committed file and `clue-source: release` downloads the same pair, and either way an absent entry fails the run rather than letting an unlisted binary execute. The bare names are a public contract with the reusable workflow and the install scripts under `guide/public/`, not an implementation detail ([ADR-030](../../decisions/ADR-030-verified-install-scripts.md)). `TestSanity_ReleaseKeepsTheAssetNamesTheAdopterWallInstalls` and `TestSanity_InstallScriptsUseTheReleaseAssetContract` tie the emitted names to both, so they cannot drift apart silently.

No package-manager publisher is configured. Homebrew formula generation is deprecated upstream and its replacement, casks, is macOS-only, so no single channel covers all three platforms; the install scripts do, and winget or a cask can be added later without disturbing the assets either would repackage.

That the two versions in fact agree is checked, not assumed. That gate runs `clue validate --forbid-changes` from source with the tag stamped in (`go run -ldflags "-X main.version=${VERSION}" ./cmd/clue`), so `checkSkillVersions` judges the release candidate exactly as an adopter's installed binary will judge their checkout. A tag that disagrees with the shipped skill stamp fails there, naming both versions, instead of publishing a self-inconsistent pair whose only symptom is unexplained drift in an adopter's repository. Reusing the shipped rule keeps one definition of the invariant — no second, shell-resident copy that can drift from `checkSkillVersions` — and `TestSanity_ReleaseRunsTheJudgeStampedAsTheTag` holds the step, its stamp, and its position ahead of the build and the publish step. That test reads the step's own arguments out of the workflow and runs them against temporary corpora: a lagging skill stamp must be refused with both versions named, an agreeing stamp admitted, and an undigested workspace refused — the gate is judged by what it does, not by how it reads.

When `internal/migrate/` changes, the release workflow also requires a non-empty `### Migration` section in the tag's changelog notes before it spends the version. That section is the adopter-facing path for any added or narrowed corpus obligation; releases that leave the migration registry untouched keep the ordinary notes contract.

Installation is a checksum-verifying script published with the guide ([ADR-030](../../decisions/ADR-030-verified-install-scripts.md)): `guide/public/install.sh` for macOS and Linux, `install.ps1` for Windows, both served from `cliewen.dev` by the same Pages deployment as the guide. `go install github.com/cliewen/cliewen/cmd/clue@vX.Y.Z` builds from source and self-stamps from Go's build info, and `gh release download vX.Y.Z` fetches a stamped prebuilt binary — the documented manual fallback and one source supported by the reusable workflow.

## Deliberate limits (doors, not gaps)

- **Skills outside `.agents/skills/`** — the rule looks only there. An adopter who relocates skills gets no drift check until the path is made configurable.
- **Untagged installs report `dev`** — `go install module@vX.Y.Z` self-stamps from Go's build info, but a checkout build or an install of a branch/commit (a pseudo-version) has no release to report and stays `dev`, exempt from drift.
- **No background upgrade** — this repository's `clue` release edits the shared generated-skill frontmatter source, regenerates the six skill artifacts, and tags. Its release gate checks the candidate before publication; an unpublished tag can be retargeted to a repaired main commit, while a GitHub Release object makes its version immutable. This distribution process does not define or constrain an adopter's release process. `clue migrate` is the explicit reviewed updater for the supported corpus and managed-carrier migrations; `clue init` still skips existing files, and unknown or locally modified carriers remain a human repair rather than an overwrite.
- **A dry run cannot prove the release page** — `--skip=publish` produces the full artifact set, which is how asset names and the checksum format are checked before a tag is spent, but it creates no release, so it can say nothing about the body. v0.8.0 shipped a blank page with every dry run and every structural assertion green. Anything about what a release *displays* is proven by a published release and by the post-publish verification, never by a local run.
- **Release assets are append-only** — a new distribution channel may add assets; it may never rename or remove one, because the bare binary names are executed by a workflow vendored into repositories we do not control, and by the published install scripts ([ADR-030](../../decisions/ADR-030-verified-install-scripts.md)). A rename surfaces in an adopter's CI as a broken run with no local change to explain it, and in a stranger's terminal as a failed install.
- **The release list is one host's** — the check asks GitHub, where Cliewen publishes. A mirror or a private redistribution has no way to answer it, and the check reports "could not tell" rather than being wrong; making the source configurable is its own change.
- **No package manager leads** — Homebrew formula generation is deprecated upstream and casks are macOS-only, so none covers all three platforms. winget and a macOS cask are wanted additions, each its own change; neither blocks a working install.
- **Upgrades are half an upgrade** — re-running the install script moves the binary, never the committed skills, so it produces a legitimate drift report in an already-adopted repository. The coordinated set stays a reviewed change, as `guide/operations.md` states.
- **The install scripts are not exercised by CI** — their contract with the asset names is tested, and both were run end to end against a real release before merge (`install.ps1` under Windows PowerShell 5.1 *and* PowerShell 7, since only 5.1 ships with Windows and the two differ in how they expose a redirect), but no job installs `clue` on three operating systems on every push. The operational proof stays the first user on a platform.
- **The `.exe` suffix is goreleaser behaviour, not configuration** — `install.ps1` and the release agree that the Windows asset ends in `.exe`, and `TestSanity_InstallScriptsUseTheReleaseAssetContract` holds the script to it, but nothing in `.goreleaser.yaml` states it: the suffix comes from the archive pipe carrying the build's extension. Both tests stay green if that behaviour ever changes, and the Windows install would 404. Proving it needs a job that actually runs goreleaser and asserts the six emitted names — the same job the previous limit describes.

## Reporting a newer release

`internal/release.Check` reads one fact from the published release list — the newest tag — and returns a report rather than an error, because every way of failing to get that fact means "could not tell" and none of them says anything about the repository. `clue latest` prints it: both versions, and when behind, one installation route resolved from the running machine (the PowerShell script on Windows, the shell script on macOS and Linux, `go install` pinned to the named release where `.goreleaser.yaml` publishes no asset) followed by the `clue migrate` preview-and-apply sequence. A source build reports `dev` and is exempt from the comparison, the same exemption the drift rule makes and for the same reason.

A tag is accepted only as exactly three decimal numbers, and the reported version is rebuilt from those numbers rather than echoed from the response — the printed recipe is a command the user runs, so the string that was checked and the string that is printed must be the same string. The cache is read under the same rule. The running stamp is local and never printed as a command, so a pre-release suffix is trimmed and the numbers compared, with a pre-release ordered before the release it names and build metadata ordered with it; a stamp that still cannot be read is reported as uncomparable rather than as current, and a stamp ahead of the newest published release is reported as unpublished rather than as that release.

Everything reaching outside the process is injected — the network, the clock, the cache directory, and the platform — so all three routes and every degradation are proven without a live service and without three machines. The answer is cached at `<user cache dir>/cliewen/latest-release.json` for 24 hours; missing, stale, unparseable, future-stamped, and unwritable are one outcome, absence, since a cache that can fail a command is worse than no cache. An unknown answer is never cached *as an answer*, so an outage can never invent a version or silence a call the user made.

The file records the other outcome too, and separately: **when the release list does not answer, that is remembered for an hour** under its own field, and only a check nobody asked for honours it (AC-088). Without this the day-long cache's promise held only when the list answered — every workflow command in an offline or blackholed session paid the ambient budget again for the same non-answer. An hour is the lifetime because a non-answer is a fact about a moment rather than about the world: it covers one sitting of work and GitHub's rate-limit window, and it does not punish someone for the rest of the day for having fixed their network. "Does not answer" is the whole set AC-077 already treats as one outcome — offline, a timeout, a rate limit, and a reply the command does not recognize — rather than transport failure alone: a rate limit is precisely the case the hour is sized for, and it arrives as a reply. The asymmetry is the safeguard — `clue latest` always asks, so remembering a failure can bound what an unrequested check costs without ever hiding the answer from someone who wants it. The failure is stored under an explicit field rather than as an empty tag, so a truncated or self-contradictory file stays absence: ADR-042's rule that an unreadable cache is ignored is unchanged, and only a file that parses cleanly and says so can suppress a request.

The command is outside the judge permanently and must never be a required status check, and it writes no file in the repository with or without flags ([ADR-042](../../decisions/ADR-042-release-check-outside-the-judge.md)). `--quiet` prints one line when behind and nothing otherwise.

That mode has two callers, and the second is the one that does the work ([PDR-023](../../decisions/PDR-023-tool-notice-and-hub-instruction.md)). The materialized `AGENTS.md` asks the agent to run the check before its first tool call, which covers a session that runs no `clue` command at all. And `clue` itself volunteers the same line: **the workflow commands — `init`, `scaffold`, `context`, `migrate`, `refs` — print the notice to standard error when a newer release exists**, so an agent learns it is behind as a consequence of work it was already doing rather than by remembering to ask. The hub's line was tried alone first and observed failing under AC-085; the notifier is what replaced it as the mechanism.

The gate is where the exclusions live, and each one is a decision. `clue validate` never carries the notice: the judge's verdict, exit code, and output stay a statement about the repository alone. `clue version` never carries it, because it is the one command guaranteed to answer instantly, offline, and identically forever. `clue latest` never carries it, because it is the check. Beyond the command, the notice requires `CI` to be empty or unset and `CLUE_NO_UPDATE_NOTIFIER` to be absent — so a runner never reaches the release list, and anyone who wants silence has one documented switch. The asymmetry is deliberate: `CI=` is how a shell says "this is not CI", so reading a set-but-empty one as a runner would silence the notice on the developer machines that spell it that way, while the opt-out is a switch a person sets and `CLUE_NO_UPDATE_NOTIFIER=` — what a wrapper script or a templated matrix produces — must switch it off. The ambient budget is shorter than the requested check's, because a notice nobody asked for must never be something the user can feel; the day-long cache means it is paid at most once a day when the list answers, and the remembered non-answer above bounds it to once an hour when it does not. Both callers share one phrasing of the line, so the two cannot drift into saying the same fact differently.

**There is deliberately no terminal condition, and its absence is the load-bearing part.** An earlier gate required standard error to be a character device, which excluded every coding agent: an agent captures a command's output through a pipe rather than watching it on a terminal, so the notice was switched off in exactly the sessions it exists for, leaving only the prose fallback already observed failing. `CI` carries the ephemeral-runner rejection by itself. What a terminal check uniquely protects is narrower than it appears — a script consumes standard output and an exit code, and both stay byte-identical with the notice and without it, which is the property AC-086 states and a subprocess run of the built binary proves. AC-087 holds the direction that failed, driving the notice through a real pipe rather than a buffer that was never a terminal to begin with.

The notice reaches standard error after the command it rode in on, so no command's output is interleaved with it and none of it lands on standard output. Nothing about the check itself changes for either caller — silence when current, offline, or unable to tell was already the contract. One gap is inherent and named rather than solved: a binary old enough to lack `clue latest` also lacks the notifier, so it can announce nothing. The hub tells the agent to read `unknown command "latest"` as the answer it is — that binary is behind — and the gap closes after one upgrade.

**What the notice routes to is simple work** (AC-142, [PDR-043](../../decisions/PDR-043-upgrade-routes-as-simple-work.md)). The upgrade skill states its own route rather than sending the agent to the generic tier text for it, because that text is generic by design and cannot know the thing that decides this case: the release's contract changes were argued and accepted upstream, so the adopting repository's own accepted contract is unchanged by moving onto them. Left unstated, the tier rule reads a rewrite of six skills, a caller, and corpus shape as methodology meaning and answers full — observed twice in an adopter, at the cost of a change identity, a workspace, and an acceptance brief for a preview, an apply, and a binary swap. The skill's router therefore reaches the workflow before change routing, and change routing is reached for the one thing that genuinely escalates: a decision of the repository's own that applying the release forces.

**Release availability and repository currency are separate checks** (AC-148 and AC-149, [PDR-043](../../decisions/PDR-043-upgrade-routes-as-simple-work.md)). `clue latest` asks whether a newer CLI release is published; it cannot inspect committed managed carriers. The upgrade skill therefore runs `clue migrate` without `--apply` immediately afterwards, including when the installed release is the newest or the release list is unavailable, and treats its planned changes, findings, or notices as drift. A clean preview says that the managed carriers match the installed binary; the agent may call the repository current only when the release list was reachable and reported no newer release as well. When the release list is unavailable, the agent reports published-release freshness as unknown and stops if the local preview is clean. The preview remains read-only until the human authorizes the coordinated upgrade.

## Resolving external addresses

`clue refs` follows what the corpus points at and classifies each address reachable, restricted, redirected, gone, or unreachable. Only a gone address is an error: a restricted target — a private repository, an internal wiki — is a permanent and correct answer, and a timeout or a rate limit is reported as unknown, so another organisation's downtime can never condemn a corpus that has not changed. It previews by default and rewrites redirected addresses only under `--apply`, never inside a completed plan, whose addresses record what was observed at the time. A credential is sent only to the service that issued it, and only where that service honours it. The command is deliberately outside the deterministic judge and must never be a required status check ([ADR-040](../../decisions/ADR-040-qualified-external-references.md)).
