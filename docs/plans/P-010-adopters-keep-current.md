# P-010 — Cliewen makes staying current something an adopter notices

This campaign is [P-009](P-009-migration-readiness.md)'s successor, and it is designated here rather than in P-009's own digest because CH-099 deliberately closed that campaign without naming one and [C-008](../constraints/C-008-completed-plans-immutable.md) freezes it afterwards. The forward link can only live on this side of the boundary.

P-009 gave corpus releases a previewable mechanical upgrade path and closed on it. What it did not give anyone was a reason to run that path, or a place to learn it exists. `clue migrate` is named in an adopted repository — in three of the five skills, in the emitted `CLAUDE.md`, and in the emitted `docs/README.md` — but never as something to go and do: the skills mention it only inside the shared local-conventions paragraph, as a precondition of a change already under way, so an agent asked to bring a repository up to date meets no entry point. The word "upgrade" occurs in none of the five generated skills or their canonical sources, and the emitted routing hub names neither upgrading, migrating, nor versions — and that hub is the adopter's file, which `clue init` never overwrites and `clue migrate` never rewrites, so routing added there reaches new repositories only. Only skills reach an adopter who has already onboarded.

Worse than absent guidance is confident silence. An old binary carrying matching old skills validates green, and `clue migrate` on that pair reports "no changes needed" — a sentence an adopter reasonably reads as "you are current". Nothing in the system distinguishes being up to date from being unable to tell. The one moment a repository does learn something is wrong is the drift message, which names no command that would fix it.

Three backlogs were also routed forward across P-007, P-008, and P-009 without a campaign that owns them, and the judge reports all three by count. When this campaign opened it reported 27 decisions still `inferred` — agent-authored and never human-verified — 13 constraints whose only enforcement is an agent remembering to read them, and four capabilities contradicted by AN-007, AN-011, and AN-013. Those figures are the condition at opening, not a standing claim; the campaign's own progress moves them, and the milestones below are written against what the judge reports rather than against a number fixed here. A methodology whose core promise is that humans verify meaning and machines enforce form cannot leave nearly half its own decisions unverified and all but two of its own constraints unenforced by any machine.

This campaign runs in two arcs. The first makes staying current visible and actionable: a command that reports a newer release and shows the recipe for the machine it is actually running on, routing that reaches existing adopters through a skill rather than through a file Cliewen may not touch, and discovery at the moment a coding agent starts or its context window is restarted. The second clears the three backlogs. Every milestone is a separate full Cliewen change rooted at accepted `main`, published as a ready pull request, and accepted by human merge before the next begins. Milestone numbering continues corpus-global numbering from P-009.

## Explicitly out of this campaign

**Simplification is deferred to P-012.** It is real work and it is deliberately not folded in here: a campaign that carries both would let "we should simplify first" postpone three backlogs that have already waited through three campaigns. P-011 instead addresses the brownfield-migration contract that later evidence established as the higher-risk boundary ([PDR-025](../decisions/PDR-025-brownfield-migration-precedes-simplification.md)).

**The judge never reaches the network.** No milestone puts a network call inside `clue validate` or anywhere a validation verdict can read it. The separation is the point of M-045's decision record, not an implementation detail of it.

**`clue` does not replace its own binary.** The installation scripts verify every download against the release's published checksums and refuse to install on a mismatch; a self-updating binary would have to reimplement that verification inside itself, and a program that can overwrite itself from the network is a different kind of program than an offline judge. The convenience an adopter asked for is delivered by an agent following the skill, under the human merge boundary, not by the command.

**No milestone emits configuration for an assistant.** M-047 was revised to this position rather than written with it: its original exit criterion required the scaffold to emit a vendor's session-start configuration, and that was rejected during CH-109 as a violation of Cliewen's agent-agnosticism. The method belongs to no assistant, so nothing here ships a file that tells one what to run — in an adopted repository or in this one ([PDR-023](../decisions/PDR-023-tool-notice-and-hub-instruction.md)).

**And prose alone did not carry it.** M-047 was revised a second time, in the same change, after its replacement failed its own acceptance test: the hub's instruction reached a real session and the agent read past it into the requested work. The milestone now puts the mechanism in the tool — a notice the workflow commands volunteer — and keeps the hub's line as the fallback for sessions no command reaches. This is recorded because the sequence is the useful part: agnosticism ruled out the reliable mechanism, the obvious replacement was assumed to be good enough, and it took a Human criterion actually being run to find out that it was not.

**And the replacement's first gate excluded the audience.** M-047 was revised a third time, still in the same change, when review found the notifier required a terminal — which a coding agent never gives a command, because it captures the output instead. Every unit test of the gate passed while the mechanism reached nobody it was built for. The pattern across all three revisions is the same one: each time, the thing that failed was assumed rather than observed, and each time it took running the real path to see it. A criterion about a session learning something is worth more than any number of assertions about the parts.

**No milestone weakens the human merge boundary.** Nothing here lets an agent upgrade a repository and accept the result, and the automatic discovery in M-047 informs a session; it never acts on its own.

## Mutation rules

Status and evidence fields in the milestone table may mutate in an implementing change's merge digest. Everything else changes only through a declared plan revision backed by a decision record routed by reversal cost. Plan adjustments are decisions.
